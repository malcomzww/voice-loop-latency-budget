# Voice loop latency: what holds on any machine

Generated by `python scripts/generate_results.py`. Do not edit by hand.
Absolute timings live in `results/waterfall-raw.md`, which is gitignored
because CPU inference speed is hardware-dependent and byte-comparing
milliseconds across machines is a broken CI gate. The claims below are
the portable ones, and this script exits non-zero if any breaks.

**The LLM hop is SIMULATED.** No API key was configured, so no live
model was ever called. It is a synthetic delay with a configurable
time-to-first-token. VAD, ASR and TTS are real measured engines.

## 1. Which hop dominates

**ASR dominates**, taking more than **70%** of measured hop
time at p50 in the default configuration (partials on, greedy decoding).

Hops ranked by p50 cost. Ranking is reported rather than percentages
because a share depends on every other hop; the order does not.

| rank | hop | measured or simulated |
|---|---|---|
| 1 | asr | measured |
| 2 | tts | measured |
| 3 | llm | **SIMULATED** |
| 4 | vad | measured |
| 5 | playback | measured |

ASR costs more than TTS and VAD combined. This holds regardless of
machine speed, because all three scale together with CPU throughput.

VAD *compute* is negligible -- a fraction of a percent. That is not the
same as the VAD being free; see section 4.

## 2. The one optimisation that mattered: drop the partials

Whisper is not a streaming model. Partial hypotheses are implemented
by re-transcribing a growing buffer, so every partial is a full
forward pass over everything said so far, and the last partial costs
nearly as much as the final transcription it is about to duplicate.

Turning partials off cuts p50 ASR compute by more than **50%**,
which is the largest single change available anywhere in this loop.
This script asserts the factor exceeds 1.5x and re-checks the band.

The trade is real and worth stating: partials are what let a UI show
text while the user is still speaking. The measurement says what that
costs, not that nobody should pay it. The exact multiple is left to the
raw file rather than banded here -- it swings with CPU contention, and
only the direction and rough size of the effect are portable.

The fix is architectural rather than a tuning knob. A true streaming
model (CTC or RNN-T) emits partials from a single forward pass over
each new frame, so interim text is nearly free. Whisper's encoder-
decoder shape is what makes partials expensive here, and no amount of
interval tuning removes that -- it only trades interim text for cost.

## 3. First chunk, not total audio

The claim behind `docs/adr/0001-first-chunk-not-total-audio.md`.

- Piper yields its first chunk well before it finishes the utterance:
  the first chunk is playable within **60%** of total
  synthesis time at p50.
- Synthesis runs at least **10x faster than
  real time**, so playback of chunk *n* covers synthesis of chunk *n+1*
  and the stream never underruns.
- Median reply across all turns is over **3 s** of
  audio. Waiting for all of it before playing delays the first phoneme
  for no audible benefit, because the rest is synthesised faster than
  it is heard.

Streaming the first chunk instead of buffering the utterance is a
**strict improvement**: identical audio, earlier start, asserted here to
be a positive saving on every run.

## 4. The VAD costs almost no compute and a lot of latency

The most misleading row in any voice-loop budget. Silero scores a
32 ms frame in well under a millisecond, so a naive table reports the
VAD as ~0% and moves on. But endpointing is a *waiting* decision: the
loop cannot call the ASR until it believes the user stopped, and that
belief costs the full hangover in silence.

| hangover | added to every turn |
|---|---|
| 200 ms | 200 ms, exactly |
| 500 ms | 500 ms, exactly |
| 800 ms | 800 ms, exactly |

The hangover enters perceived latency one-for-one, which makes it the
cheapest knob in the loop -- and the one with a hard floor, since
cutting it too far truncates the user mid-sentence. It is a
turn-taking accuracy trade, not a compute trade.

## 5. Perceived latency is not the sum of the hops

Summing hop durations double-counts overlapped work. The budget uses
a merged critical path so the parts sum to the whole; see
`critical_path` in `src/voice_loop_latency_budget/tracer.py`.

## Limitations

- **The LLM hop is simulated.** These results establish nothing about
  any provider's real TTFT. The stub exists so the *decomposition* is
  honest and TTFT can be swept; a live endpoint would add one
  provider's network variance on one afternoon and measure that.
- **Synthetic speech in, synthetic speech out.** Prompts are Piper
  output, not human recordings, so no collected audio or speaker data
  ships here. TTS output is unnaturally clean input for a VAD and an
  ASR: real microphones bring noise, clipping and far-field reverb
  that would raise ASR cost and hurt endpointing. **These numbers are
  a floor, not a forecast.**
- **Accuracy is not measured.** The repo measures latency only. Greedy
  decoding and `tiny.en` are latency choices; their WER cost is real
  and unquantified here.
- **Single machine, CPU only, no GPU.** A GPU changes the ASR/TTS
  balance and could well move which hop dominates.
- **No barge-in.** The loop does not handle the user interrupting
  playback, which is a real turn-taking cost this budget ignores.
